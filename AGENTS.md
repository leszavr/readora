# Readora Agent Guide

Этот файл обязателен к прочтению в начале каждой рабочей сессии по проекту Readora.

## 0. Язык общения агента

- Всегда пиши видимые ответы пользователю и рабочие пояснения на русском языке.
- Исключения допустимы только там, где нужен оригинальный текст: код, имена API/файлов/команд, технические термины, логи, ошибки, идентификаторы и цитаты.

## 1. Контекст проекта

Readora — личная веб-библиотека для загрузки и чтения книг в форматах FB2 и EPUB.

Текущий код — TypeScript-монорепозиторий на pnpm с React/Vite-фронтендом, Express API, PostgreSQL и Drizzle ORM.

Ключевая структура:

```text
artifacts/readora/       # React frontend, Vite, Tailwind, shadcn/Radix-style UI
artifacts/api-server/    # Express API, авторизация, маршруты и серверные сервисы
lib/db/                  # Drizzle schema, миграции и подключение к PostgreSQL
lib/api-spec/             # OpenAPI-спецификация — источник API-контрактов
lib/api-client-react/     # Сгенерированный React Query API-клиент
lib/api-zod/              # Сгенерированные Zod-схемы
scripts/                 # Вспомогательные скрипты
uploads/                 # Локальное хранилище загруженных файлов в dev
```

Перед изменениями сверяйся с релевантной документацией:

- `README.md` — запуск, структура, переменные окружения и архитектурные решения;
- `CONTRIBUTING.md` — правила внесения изменений;
- `artifacts/readora/src/` — текущая клиентская архитектура и UI-паттерны;
- `artifacts/api-server/src/routes/` — существующие API-контракты и проверки доступа;
- `lib/db/src/schema/` — актуальная схема базы данных;
- `lib/db/migrations/` — применённые миграции;
- `VOXLIBRIS.md` — только если задача затрагивает связь Readora с VoxLibris.

## 2. Главный принцип разработки

- KISS и YAGNI важнее «идеальной» архитектуры.
- Делай только то, что нужно для текущей задачи.
- Не добавляй абстракции, слои, фабрики, интерфейсы и универсальные сервисы «на будущее».
- Не создавай новую подсистему, если существующую можно безопасно расширить.
- Не меняй большой набор файлов ради локальной задачи.
- Перед изменением shared/core-логики найди usages и оцени влияние.
- Если решение становится сложным, остановись, объясни причину и предложи более простой вариант.
- Не используй «MVP» как оправдание для заглушек, небезопасных допущений, отсутствия серверных проверок или неподдерживаемого кода.

Красные флаги:

- интерфейс с одной реализацией;
- новый слой без реальной необходимости;
- дублирование существующего модуля вместо его расширения;
- опасная миграция ради удобства разработки;
- UI-скрытие без серверной проверки;
- изменение публичного контракта без поиска всех потребителей;
- публикация пользовательских данных без явного продуктового основания.

## 3. Package manager и команды

- Используй `pnpm`, не `npm` и не `yarn`.
- Node.js: `24+` согласно `Dockerfile` и `README.md`.
- pnpm: `10+`, в проекте зафиксирован `pnpm@10.19.0`.
- Не устанавливай зависимости без явной необходимости.
- Перед добавлением зависимости проверь, нельзя ли решить задачу текущим стеком.

Основные команды:

```bash
pnpm run dev:server                 # Express API
pnpm run dev:client                 # Vite frontend
pnpm run build                      # typecheck и production build
pnpm run typecheck                  # проверка типов всех пакетов
pnpm run check                      # алиас общей проверки типов
pnpm run db:generate                # сгенерировать миграцию Drizzle
pnpm run db:migrate                 # применить миграции
pnpm run db:migrate:status          # статус миграций
pnpm --filter @workspace/api-server test
pnpm --filter @workspace/api-server typecheck
docker build -t readora-check .
```

Для нетривиальных изменений по возможности запускай минимальную релевантную проверку:

- только TypeScript/API/shared: `pnpm run typecheck`;
- изменения сервера: `pnpm --filter @workspace/api-server typecheck` и релевантные тесты;
- изменения фронтенда: `pnpm --filter @workspace/readora typecheck`;
- изменения миграций: `pnpm run db:migrate:status`, затем typecheck/build;
- перед крупным завершением: `pnpm run build`;
- изменения Docker/production build: `docker build -t readora-check .`.

Если проверку нельзя выполнить из-за окружения, прямо укажи причину и что именно не проверено.

## 4. Миграции базы данных

Проект использует версионированные SQL-миграции Drizzle в `lib/db/migrations/`. Не подменяй миграцию командой `db:push` для production-изменений.

Перед созданием миграции:

```bash
ls lib/db/migrations/ | sort | tail -5
```

Обязательные правила:

1. Соблюдай последовательность миграций и формат, уже принятый в проекте.
2. Для аддитивных изменений используй безопасные конструкции, где это совместимо с текущим migration runner: `IF NOT EXISTS` для новых колонок и индексов.
3. Не изменяй уже применённые миграции.
4. Не выполняй без явного согласования `DROP`, `TRUNCATE`, разрушительные изменения типов или удаление данных.
5. Сначала обнови Drizzle-схему, затем создай миграцию и проверь её содержимое.
6. Учитывай production-деплой через Docker/CapRover: миграции не должны незаметно запускаться из application startup, если это не предусмотрено текущим процессом деплоя.

## 5. Инфраструктура и окружение

- База данных: PostgreSQL 16, подключение через `DATABASE_URL`.
- Авторизация: cookie-сессии `express-session`, хранящиеся в PostgreSQL. Не заменяй их JWT без отдельного решения.
- Файлы книг и исходные обложки: серверное файловое хранилище, путь задаётся через `UPLOADS_DIR`.
- Production: один Node/Express-контейнер в Docker, деплой через CapRover.
- Frontend в production собирается Vite и раздаётся Express из каталога `client`.
- Секреты и пользовательские данные не должны попадать в логи, ответы публичных API или клиентские бандлы.

Не меняй Docker-процесс без проверки всего production-пути: сборка workspace, `pnpm deploy`, расположение `dist`, клиентская статика и команда запуска должны оставаться рабочими.

## 6. Архитектурные паттерны проекта

- Express-маршруты создавай через `Router()` и подключай через существующий `artifacts/api-server/src/routes/index.ts`.
- Для приватных маршрутов используй существующий `requireAuth` и проверяй владельца ресурса на сервере.
- Для БД используй Drizzle ORM и существующие таблицы/схемы.
- Не используй `sql.raw()` с пользовательскими данными.
- Для списков и фильтров используй безопасные конструкции Drizzle (`inArray`, `sql.join` и аналогичные существующие паттерны).
- Входные данные валидируй существующими Zod-паттернами проекта.
- OpenAPI в `lib/api-spec` является источником публичных API-контрактов. Перед изменением контракта найди всех потребителей и обнови связанные generated-пакеты, если это принято для данного изменения.
- На фронтенде сохраняй React/Vite/Tailwind/TanStack Query/wouter-подходы проекта.
- Не смешивай SSR-логику с приватными данными сессии без необходимости; HTML лендинга должен быть безопасен для кэширования.

## 7. UI/UX правила

- Сохраняй текущий дизайн, компоненты `components/ui` и Tailwind-паттерны.
- Не ломай существующую дизайн-систему без причины.
- Для новых интерфейсных состояний реализуй загрузку, ошибку и empty state, если они применимы.
- Проверяй мобильную адаптацию.
- Не добавляй публичные ссылки на приватные книги, главы, файлы или личные страницы.
- UI-ограничения доступа всегда дублируй серверной проверкой.
- Не используй `dangerouslySetInnerHTML`, если задача не требует этого явно и данные не прошли строгую санитизацию.

## 8. Безопасность и пользовательские данные

- Приватные API обязаны использовать существующий auth middleware.
- Проверяй права на уровне route/service, не доверяй клиентским флагам.
- Не отдавай содержимое книги, файл, прогресс, `ownerUserId`, storage key или приватные метаданные без доказанного права доступа.
- Публикация данных на лендинге должна быть ограничена ровно согласованным публичным контрактом.
- Не отдавай в публичных ответах внутренние ID, счётчики, file hash и служебные поля, если они не нужны клиенту.
- Валидируй и ограничивай длину пользовательских строк.
- Не логируй пароли, токены, содержимое книг, сессионные данные и приватные пользовательские метаданные.
- Не помещай секреты в `.env.example`, исходники или frontend bundle.
- Не используй внешние сервисы или зависимости для пользовательских данных без явного требования и оценки риска.

## 9. Как начинать каждую задачу

1. Прочитай пользовательский запрос и определи затрагиваемые слои: frontend, API, DB, auth, deployment или docs.
2. Проверь `AGENTS.md`, локальные правила в поддиректориях и релевантную документацию.
3. Проверь текущее состояние git и не перезаписывай незапрошенные изменения.
4. Найди существующую реализацию и usages перед добавлением нового кода.
5. Если меняется core/shared/public contract, оцени влияние на frontend, API, generated-клиент и тесты.
6. Для миграции проверь последнюю миграцию и создай новую, не редактируя старые.
7. Выбери самое простое решение, которое закрывает задачу без хаков.
8. После изменений запусти минимальную релевантную проверку.
9. В финальном ответе укажи: что изменено, чем проверено, что осталось непроверенным или рискованным.
10. Если задача явно сформулирована, выполняй её целиком без промежуточных запросов, если нет блокирующего решения, риска или отсутствующих данных.

## 10. Когда спрашивать пользователя

Спрашивай только если решение реально блокируется выбором или риском:

- требуется разрушительная миграция или изменение production-контракта;
- есть неоднозначный продуктовый сценарий;
- нужно публиковать пользовательские данные с риском приватности или авторских прав;
- требуется новая внешняя зависимость, сервис или инфраструктура;
- документация и текущий код противоречат друг другу;
- отсутствуют необходимые credentials или production-доступ.

Не спрашивай о мелочах, которые можно решить по существующим правилам проекта.

## 11. Экономия токенов и анти-оверинжиниринг

- Отвечай сжато: изменения, проверки и только необходимые пояснения.
- Не генерируй очевидные комментарии в коде.
- Не создавай интерфейсы для единственной реализации без необходимости тестирования или DI.
- Не добавляй Factory/Strategy/Observer и другие сложные паттерны без реальной потребности.
- Не добавляй поля «на будущее» и гипотетические функции.
- Предпочитай простые функции и прямую логику.
- Если задача большая, разбивай её на проверяемые этапы, но не оставляй незавершённые слои без явного объяснения.

Перед добавлением кода спроси себя: «Это действительно необходимо для текущей задачи?»
