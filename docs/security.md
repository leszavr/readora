# Readora — безопасность

## Модель угроз (кратко)

Readora хранит приватные пользовательские данные: файлы книг, прогресс, заметки, email. Основные злоумышленники: неавторизованный посетитель (доступ к чужим книгам/файлам), легитимный пользователь (эскалация до админа/модератора, обход квот), компрометация БД/бэкапов (пароли, токены, креды облаков).

## Аутентификация и сессии

- Пароли — bcrypt cost 12. Токены (remember, email-верификация, сброс/смена пароля) хранятся в БД **только как sha256-хэши** (миграция 0030).
- Cookie-сессии httpOnly + sameSite=lax + secure в production; хранение в PostgreSQL; rolling-продление 30 дней; порог неактивности 30 дней.
- Сброс пароля инвалидирует все сессии пользователя. Режим обслуживания — массовый logout.
- Вход через Яндекс ID и VK ID (OAuth state с защитой от replay).
- Удаление аккаунта: 8-значный код подтверждения, grace period 30 дней, восстановление через поддержку (restore/purge в админке).

## Авторизация

Три роли: `user`, `moderator`, `admin` (см. [architecture.md](architecture.md)). Правила:

- Проверка прав на уровне route/service — UI-ограничения всегда дублируются сервером.
- Проверка владельца ресурса: содержимое книги, файл, прогресс, заметки, метаданные — только владельцу.
- `requireSystemAdmin` (только admin): управление пользователями, настройками, SMTP, аналитикой, отзывами, письмами, мутации подарочных изданий. Модератор не получает доступ к приватным данным пользователей.
- Подарочное издание создаётся **только из собственной книги администратора** — публикация чужих книг запрещена на сервере (403).

## Данные и файлы

- Файлы книг отдаются исключительно через API с проверкой доступа; прямой доступ к хранилищу закрыт. Путь `UPLOADS_DIR` вне статики.
- Креды внешних хранилищ — AES-256-GCM (`EXTERNAL_STORAGE_ENCRYPTION_KEY`).
- В публичных ответах нет внутренних ID владельцев, storage key, file hash и служебных полей. Лендинг/SEO-страницы не содержат приватных данных и безопасны для кэширования.
- В логи не пишутся пароли, токены, сессии, содержимое книг и приватные метаданные.

## Ввод и лимиты

- Zod-валидация всех входов (сгенерированные схемы из OpenAPI); ограничения длины строк.
- Rate-лимитеры (по IP, с нормализацией IPv6) на событиях аналитики и публичных формах (feedback, PWA, сброс пароля).
- Экранирование: CBZ-контент, email-шаблоны (аудит 2026-11-03). `dangerouslySetInnerHTML` — только после строгой санитизации.
- Лимиты загрузки: размер файла (настраивается, default 50 МБ), число глав (3000), квота библиотеки per user; админ без лимитов.

## Аналитика и приватность

- Продуктовая аналитика — opt-in при регистрации, отключается в профиле; хранятся только события чтения и агрегаты без содержимого книг.
- Аудит-вехи: аудит безопасности 2026-11-03 (requireSystemAdmin, sha256-токены, экранирование, обновление зависимостей), лимитер IPv6 2026-11-07.

## Известные границы модели

- In-memory presence (`/admin/online-users`) обнуляется при рестарте процесса — это осознанный компромисс (один контейнер, KISS).
- Брутфорс-защита логина полагается на rate-лимитеры и bcrypt cost; отдельной блокировки по аккаунту нет.
