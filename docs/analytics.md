# Аналитика

Readora использует два независимых self-hosted слоя аналитики:

- приватную продуктовую аналитику событий чтения, которая включена по умолчанию для новых пользователей и может быть отключена в профиле;
- системные и маркетинговые агрегаты для админ-панели, которые строятся по основным таблицам сервиса и не зависят от согласия на продуктовую аналитику.

Настройка существующих пользователей не меняется автоматически.

Сводная аналитика доступна только роли `admin` во вкладке «Аналитика» панели управления. API возвращает только агрегаты: без идентификаторов пользователей и книг, содержимого книг и сырых событий.

## Маркетинговые показатели

В админ-панели рассчитываются регистрации, доля подтверждённых email, доля пользователей с хотя бы одной книгой, регистрации по неделям, retention D7/D30, книги на пользователя, открытия на активного читателя и доля дочитанных книг.

- Регистрации, подтверждение email и первая загрузка используют `users` и `books` за выбранный период.
- Retention D7/D30 учитывает читателей, которые открыли книгу в UTC-день регистрации и вернулись в течение следующих 7 или 30 суток. В расчёт попадают только пользователи, для которых этот срок уже завершился.
- Доля дочитанных книг — число уникальных книг с завершённым `reading_progress` к общему числу книг.
- Средняя длительность сессии относится к приватной продуктовой аналитике и поэтому отражает только пользователей с включённым сбором.

При регистрации клиент определяет только одну нормализованную категорию источника: `direct`, `telegram`, `habr`, `productradar`, `show_hn`, `reddit`, `vk`, `seo` или `other`. Для ранее зарегистрированных пользователей без такой категории в агрегате используется `unknown`.

Raw referrer, URL, UTM-метки, поисковые запросы, IP-адреса, User-Agent и идентификаторы кампаний не сохраняются и не возвращаются API. Нормализованная категория хранится в `sessionStorage` только до регистрации и записывается в профиль нового пользователя.

## Встроенный планировщик

Readora запускает обработчик каждые 15 минут, выравнивая запуск по UTC. Он не выполняет агрегирование непосредственно при запуске API: на ближайшем цикле обрабатываются все дни в постоянной очереди PostgreSQL, кроме текущего UTC-дня.

Очередь пополняется триггером БД при каждой записи аналитического события. Поэтому после рестарта сервис догоняет пропущенные дни, а поздно отправленное офлайн-событие повторно ставит свой день в очередь. PostgreSQL advisory lock не позволяет нескольким репликам обрабатывать очередь одновременно.

Пересчёт одного дня и снятие его из очереди выполняются в одной транзакции. Если во время пересчёта поступает новое событие, триггер оставляет дату в очереди для следующего безопасного пересчёта. Удаление сырых событий старше 13 месяцев выполняется пакетно и только для дней, которых нет в очереди.

Планировщик включён по умолчанию. Для отдельного процесса, который выполняет эту работу, отключите его во всех экземплярах API:

```bash
ANALYTICS_ROLLUP_ENABLED=false
```

Ручной безопасный пересчёт конкретного дня остаётся доступен для восстановления или диагностики:

```bash
pnpm --filter @workspace/scripts run analytics:rollup -- 2026-09-17
```
